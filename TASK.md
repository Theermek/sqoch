# TASK: Интерфейс оформления билетов (тестовое задание, ~60 мин)

## Цель
С нуля сделать работающий SPA-сценарий покупки билетов на мероприятие на моковых данных: от начала оформления до результата (успех / закончились места). Удобно на десктопе и на мобильном шириной **360px**.

Делай **MVP**: минимально, чисто, читаемо. Код будут разбирать вживую и просить внести небольшую правку, поэтому важнее понятная структура, чем фичи.

## Стек
- Vite + React 18 + TypeScript (strict)
- Стили: CSS Modules или один глобальный CSS с переменными. Без UI-китов.
- Состояние: `useReducer` + Context (или просто `useReducer` в корне). Без Redux.
- Без роутера: шаги переключаются через состояние.
- Без бэкенда: мок-API с `setTimeout`.
- Зависимости минимальны. Тесты опциональны (если останется время, Vitest для `validation.ts` и `pricing.ts`).

## Бизнес-правила
| Правило | Детали |
|---|---|
| Участники | от 1 до 4 в одном заказе |
| Полный билет | **2000 ₽**, возраст **≥ 14** |
| Детский билет | **1000 ₽**, возраст **< 14** |
| Сопровождение | Если в заказе есть участник < 14, в том же заказе обязателен участник **≥ 18** |
| Данные участника | имя (обязательно, не пустое после trim), возраст (целое, 0–120) |
| Email | один на заказ, обязателен, базовая проверка формата |
| Подтверждение | Перед оплатой пользователь видит состав заказа и итог и может вернуться и изменить данные |
| Исходы | успешное оформление **и** ошибка «места закончились» перед подтверждением |

Тип билета определяется **автоматически** по возрасту, пользователь его не выбирает.

## Сценарий (шаги)
1. **Мероприятие**: карточка (название, дата, место, цены, остаток мест из мока), кнопка «Купить билеты».
2. **Участники и контакт**:
   - список участников (по умолчанию 1), «Добавить участника» (скрыта/disabled при 4), «Удалить» (недоступно при 1);
   - у каждого: имя, возраст и бейдж типа билета с ценой («Полный · 2000 ₽» / «Детский · 1000 ₽»), появляется, когда введён возраст;
   - поле email;
   - живой итог внизу (на мобильном прилипает к низу экрана);
   - «Далее» валидирует форму; ошибки показываются у полей, ошибка правила сопровождения показывается блоком над списком.
3. **Проверка заказа**: список участников (имя, возраст, тип, цена), email, итог. Кнопки «Изменить» (назад на шаг 2 с сохранёнными данными) и «Подтвердить и оплатить».
4. **Результат**:
   - **Успех**: номер заказа, состав, сумма, «билеты отправлены на {email}», кнопка «Оформить ещё».
   - **Места закончились**: понятное сообщение (сколько мест осталось, если 0 — что мест нет), кнопки «Изменить заказ» (вернуться к шагу 2, данные сохранены, можно уменьшить число участников) и «В начало».
   - **Сетевая/прочая ошибка**: сообщение + «Повторить».

Во время запроса кнопка подтверждения блокируется и показывает загрузку (защита от двойного клика).

## Мок-API (`src/api/mockApi.ts`)
```ts
getEvent(): Promise<EventInfo>            // { id, title, date, venue, seatsLeft }
confirmOrder(order: OrderRequest): Promise<OrderSuccess>
// при нехватке мест reject с { type: 'SOLD_OUT', seatsLeft: number }
```
- Задержка 600–1000 мс.
- `seatsLeft` хранится в модуле и уменьшается после успешного заказа.
- **Демо-переключатель** для показа «закончились места», чтобы его можно было воспроизвести на видео. Сделай его заметным, но ненавязчивым: панель «Demo» в углу с режимом `Обычный / Места закончатся при подтверждении` **и** query-параметр `?soldout=1`. В режиме sold out `confirmOrder` реджектится, даже если на шаге 1 места были (имитация того, что их выкупили, пока пользователь заполнял форму).

## Структура
```
src/
  types.ts            // Participant, TicketType, Order, EventInfo, ApiError
  constants.ts        // PRICES, MAX_PARTICIPANTS, CHILD_AGE=14, ADULT_AGE=18
  domain/
    pricing.ts        // getTicketType(age), getPrice(age), getTotal(participants)
    validation.ts     // validateOrder(state) -> { fieldErrors, formErrors }
  api/mockApi.ts
  state/checkoutReducer.ts   // step, participants, email, status, result
  components/
    EventCard.tsx
    ParticipantForm.tsx      // одна строка участника
    ParticipantsStep.tsx
    ReviewStep.tsx
    ResultStep.tsx
    OrderSummary.tsx         // переиспользуется на шагах 2 и 3
    StepIndicator.tsx
    DemoPanel.tsx
  App.tsx
  index.css
```
Бизнес-логика (цены, правила) — **только** в `domain/`, чистые функции без React. Компоненты её только вызывают. Это главная точка для «правки при проверяющих» (например, поменять цену или порог возраста в одном месте).

## UI / UX требования
- Mobile-first, корректно на **360px** без горизонтального скролла; на десктопе контент по центру, max-width ~640px.
- Тач-цели ≥ 44px, `inputmode="numeric"` для возраста, `type="email"` и `autocomplete="email"` для email.
- Понятный индикатор шагов (1 Участники → 2 Проверка → 3 Готово).
- Доступность: `<label>` у каждого поля, `aria-invalid` и `aria-describedby` для ошибок, фокус на первую ошибку при неуспешной валидации, `aria-live` для итога и результата.
- Цены в формате `2 000 ₽` (`Intl.NumberFormat('ru-RU')`).
- Валидация показывается после попытки «Далее» или после blur поля, не на каждый символ с самого начала.

## Граничные случаи (проверить вручную)
- 1 ребёнок 10 лет → ошибка сопровождения.
- Ребёнок 10 + участник 15 → ошибка (15 — полный билет, но не взрослый).
- Ребёнок 10 + взрослый 18 → ок, итог 3 000 ₽.
- Возраст 14 → полный, 13 → детский.
- 4 участника → кнопка добавления недоступна.
- Пустое имя из пробелов → ошибка.
- «Изменить» с шага проверки сохраняет все данные.
- Sold out → «Изменить заказ» возвращает с данными.
- Двойной клик по «Подтвердить» не создаёт два заказа.
